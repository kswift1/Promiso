# 블로그 스타일 가이드 — iOS 개발자의 마이그레이션기

> 이 문서는 Claude Code에 컨텍스트로 제공하거나,
> "이 가이드 기준으로 피드백해줘" 프롬프트와 함께 사용한다.

---

## 1. 타깃 독자

**1순위**: iOS 개발자 (Swift 경험, 서버는 Firebase 의존)
**2순위**: 인디 해커 / 빌드-인-퍼블릭 관심자
**3순위**: AI 활용 개발에 관심 있는 개발자

> 독자는 Rust를 모를 수 있다. 기술 설명은 항상 "왜"를 먼저, "어떻게"는 나중에.

## 2. 톤 & 보이스

| 해야 할 것 | 하지 말아야 할 것 |
|---|---|
| 1인칭 구어체 ("나는 ~했다") | 3인칭 객관체 ("개발자는 ~해야 한다") |
| 기술 결정에 감정/사심 인정 | 억지로 객관적인 척 |
| 삽질과 실패도 솔직하게 | 성공만 골라서 쓰기 |
| 짧은 문단, 여백 활용 | 긴 단락에 내용 압축 |
| 비교할 때 선택 안 한 것도 공정하게 | 선택지를 허수아비로 세우기 |

**톤 레퍼런스 — #1 글에서 잘 된 문장들:**
- `"알고 있다. Cloud Functions의 콜드스타트다."` — 독자 생각을 먼저 받아치는 방식
- `"합리적인 비교표가 결정을 뒷받침해주지만, 출발점에는 사심이 있었다."` — 감정 인정
- `"기술 선택에는 항상 감정이 섞인다. 중요한 건 감정으로 시작하되, 근거로 검증하는 것이다."` — 관점 제시

## 3. 글 구조 원칙

### 필수 구조

```
1. 훅       — 유저 피드백 or 실제 문제 한 문장으로 시작
2. 문제     — 왜 지금 방식이 한계인가
3. 선택     — 어떤 대안을 검토했고, 왜 이걸 골랐나 (비교 근거 포함)
4. 방법     — 어떻게 할 것인가 (설계/전략)
5. 마무리   — 독자가 이 글에서 가져갈 관점 1개로 끝
```

### 훅 작성 규칙

- 첫 문장은 유저 피드백, 에러 메시지, 또는 실제 상황 묘사로 시작
- 추상적인 선언 금지 (`"오늘은 X에 대해 알아보겠습니다"` — 절대 금지)
- 2~3문장 안에 "이 글이 왜 필요한가"가 보여야 함

**좋은 예:**
```
"일정 생성이 좀 느린 것 같아요."
유저 피드백을 읽으면서 속으로 생각했다. 알고 있다.
```

**나쁜 예:**
```
"오늘은 Firebase에서 Rust로 마이그레이션하는 방법을 설명하겠습니다."
```

### 마무리 규칙

- 시리즈 예고만으로 끝내지 않는다
- 이 글의 핵심 관점을 한 문장으로 다시 찍어준다
- 그 다음에 다음 글 예고를 붙여도 됨

**좋은 예:**
```
러닝커브가 사라지면 기술 선택의 기준이 바뀐다.
우리는 이제 "배우기 쉬운가"가 아니라 "본질적으로 더 나은가"를 물을 수 있다.

다음 글: 서버 뼈대 잡기 — Axum + SQLx + PostgreSQL
```

## 4. 기술 비교표 작성 규칙

- 비교 기준은 최대 6개 (스케일 비용 / 확장성 / 안정성 / 락인 / 성능 / 안전성)
- **선택 안 한 것도 강점을 인정한다** ("Go도 충분히 좋은 선택이다. 다만 ~")
- 모든 항목에서 한 선택지가 우세하면 → 비교표 신뢰도 떨어짐, 의도적으로 트레이드오프 명시

---

## 5. 코드 블록 사용 규칙

- 개념 설명엔 실제 코드보다 **의사코드(pseudocode) 또는 다이어그램** 우선
- 실제 코드는 "이게 어떻게 생겼는지" 감 잡는 용도로만 (전체 구현 X)
- Swift 예시는 독자가 iOS 개발자이므로 적극 활용
- Rust 문법이 처음 나오면 Swift 코드와 나란히 배치

**좋은 코드 블록 예 (#1 글):**
```swift
createGroup: { group in
    if FeatureFlags.useRustAPI(.groups) {
        return try await apiClient.post("/groups", body: group)
    } else {
        return try await functions.httpsCallable("createGroup").call(data)
    }
}
```
→ 짧고, 개념(Feature Flag 분기)이 바로 보임

## 6. AI 냄새 줄이기

### 하지 말 것

- **선언적 한 줄로 끊지 않는다** — "AI다.", "Rust로 답했다." 같은 드라마틱한 마무리 금지
- **수사적 질문으로 이어가지 않는다** — "그러면 뭐가 남는가?", "공통점이 뭔가?" 같은 질문→답변 반복 금지
- **독자가 아는 것을 설명하지 않는다** — 러닝커브가 뭔지, 구글링 사이클이 뭔지 풀어쓸 필요 없음
- **소제목을 남발하지 않는다** — 2~3문장짜리 섹션은 이전 문단에 합침. 소제목은 진짜 흐름이 바뀔 때만
- **번호 리스트를 연속으로 쓰지 않는다** — 나열이 필요하면 산문 한 줄로 압축할 수 있는지 먼저 확인
- **억지 마무리를 쓰지 않는다** — 할 말이 끝났으면 그냥 끝냄. 선언문, 여운, 감동 불필요

### 할 것

- **짧고 솔직한 자기 고백** — "알고 있다.", "써보고 싶었다.", "이번이 아니면 언제"
- **사실에 정확하게** — 앱 설명, 기능, 맥락이 현재와 맞아야 함. 틀리면 신뢰 깨짐
- **짧으면 합친다** — 독립 섹션으로 세울 만큼 내용이 없으면 앞뒤에 붙임

## 7. 게시 전 체크리스트

글 올리기 전 확인:

- [ ] 첫 문장이 추상적 선언이 아닌가?
- [ ] 섹션 간 맥락이 자연스럽게 이어지는가? (갑자기 다른 주제로 점프 없이)
- [ ] 비교표에서 선택 안 한 것의 강점도 인정했는가?
- [ ] 마무리가 "다음 글 예고"만으로 끝나지 않는가?
- [ ] 독자가 이 글에서 가져갈 관점이 명확한가?
- [ ] 코드 블록이 너무 길지 않은가? (20줄 이상이면 요점만 발췌)
- [ ] 한 글에 너무 많은 개념을 우겨넣지 않았는가?
- [ ] 선언적 한 줄 마무리가 없는가? (6번 AI 냄새 체크)
- [ ] 수사적 질문이 2개 이상 연속으로 나오지 않는가?
- [ ] 2~3문장짜리 독립 섹션이 없는가?

## 9. 영어 버전 (.en.md)

한글 최종본을 기반으로 번역하되, 아래 규칙을 따른다.

### 톤
- **1인칭** — "I", "my". 한글판과 동일하게 개인적 톤 유지
- **Casual but not sloppy** — 구어체지만 문법은 정확하게
- **직역 금지** — 영어권 독자에게 자연스러운 문장으로 재구성

### 구조
- 한글판과 동일한 섹션 구조 유지
- 제목: `# From Firebase to Rust — {subtitle}`
- 시리즈명: "From Firebase to Rust: An iOS App Server Migration"
- 코드 블록은 그대로, 주석만 영어로

### 지양
- ~~과도한 수동태~~ — 능동태 우선
- ~~불필요한 격식~~ — "In this article, we will explore..." 같은 학술 톤 금지
