# Firebase에서 Rust로 — 왜 Firebase를 떠나는가

*Swift 개발자의 서버 마이그레이션기 #1*

---

"일정 생성이 좀 느린 것 같아요."

유저 피드백을 읽으면서 속으로 생각했다. 알고 있다. Cloud Functions의 콜드스타트다. 일정 시간 동안 호출이 없으면 인스턴스가 내려가고, 다음 요청이 올 때 새로 띄우느라 몇 초가 걸린다. 서울 리전(asia-northeast3)에서 TypeScript 함수가 콜드스타트되면 체감 1~5초. 유저가 "생성" 버튼을 누르고 로딩 스피너를 바라보는 시간이다.

고칠 수 있는 문제인가? Firebase 안에서는 사실상 아니다. min_instances를 설정하면 인스턴스를 상시 유지할 수 있지만, 50개가 넘는 함수에 적용하면 비용이 급증한다. 그래서 "Firebase의 한계"라고 스스로를 납득시키고 넘어갔다.

그런데 한 가지가 바뀌었다.

---

## AI가 바꾼 게임

나는 Swift 2년차 iOS 개발자다. 서버는 항상 Firebase에 맡겨왔다. Auth, Firestore, Cloud Functions, Storage — Firebase가 제공하는 풀스택 위에서 iOS 앱을 만들었다. 서버를 직접 짠다는 건 나한테 다른 세계 이야기였다.

Rust는 막연히 "언젠간 해보고 싶은 언어"였다. 소유권 시스템이라는 독특한 메모리 관리, GC 없이도 안전하다는 약속, C만큼 빠르면서 현대적인 문법. 관심은 있었지만 엄두가 안 났다. iOS 개발하면서 Rust 백엔드까지? 배울 게 너무 많았다.

그런데 AI가 그 계산을 바꿔버렸다.

Claude 같은 AI와 함께 코딩하면, 러닝커브의 의미가 달라진다. 문법을 암기할 필요가 없다. 패턴을 하나하나 익힐 필요도 없다. **이해만 하면 된다.** "왜 이렇게 동작하는지"만 알면, 구현은 AI가 도와준다. 10년 경력 개발자도 새 언어를 쓸 때 반복하는 "구글링 → 스택오버플로우 → 복붙 → 수정" 사이클이 통째로 사라졌다.

이건 단순히 편해졌다는 얘기가 아니다. **기술 선택의 기준 자체가 바뀐다는 뜻이다.**

---

## 러닝커브 없는 세상에서 기술을 고르면

보통 기술 스택을 고를 때 이런 걸 본다:

- 배우기 쉬운가?
- 레퍼런스가 많은가?
- 커뮤니티가 활발한가?
- 개발 속도가 빠른가?

이 기준들의 공통점이 뭔가? 전부 **사람이 직접 코드를 짠다**는 전제 위에 있다. AI가 코딩 파트너가 되면, 이 기준들의 가중치가 급격히 내려간다.

그러면 뭐가 남는가? 순수하게 기술의 본질만 남는다:

1. **스케일 비용** — 유저가 늘면 서버비가 얼마나 드는가
2. **확장성** — 트래픽이 100배 되면 아키텍처를 다시 짜야 하는가
3. **안정성** — 장애가 얼마나 자주 나고, 얼마나 빨리 복구되는가
4. **락인** — 나중에 다른 선택지로 옮길 수 있는가
5. **성능** — 요청 하나를 얼마나 빠르게 처리하는가
6. **안전성** — 버그를 얼마나 빨리, 많이 잡아주는가

이 6가지로만 비교하면, 재미있는 결과가 나온다.

---

## Rust vs Go vs TypeScript

현재 백엔드는 TypeScript(Cloud Functions)다. 자체 서버로 옮긴다면 후보는 세 가지였다.

| 기준 | Rust | Go | TypeScript |
|------|------|-----|-----------|
| 스케일 비용 | **최고** — GC 없음, 메모리 효율 극한 | 좋음 — GC 있지만 경량 | 보통 — V8 오버헤드 |
| 확장성 | 높음 — tokio 비동기 + 멀티스레드 | 높음 — goroutine | 높음 — 하지만 CPU 바운드에 약함 |
| 안정성 | **최고** — 컴파일이 통과하면 런타임 에러가 거의 없음 | 좋음 — 단순하지만 nil 패닉 가능 | 보통 — 런타임 타입 에러 |
| 락인 | 없음 — 네이티브 바이너리 | 없음 | Firebase 종속 (현재) |
| 성능 | **최고** — C/C++ 동급 | 좋음 | 보통 |
| 안전성 | **최고** — 소유권 시스템으로 데이터레이스 원천 차단 | 좋음 | 약함 |

Go가 Rust를 이기는 항목이 하나도 없다. Go의 가장 큰 장점은 "쉽다"인데, AI와 함께라면 그 장점이 사라진다.

> Rust를 고른 이유는 단순하다. 러닝커브를 빼면 Rust가 모든 면에서 낫다.

---

## 현재 상태 — Firebase 위의 Promiso

여기서 잠깐, 내가 뭘 바꾸려는 건지 규모를 짚고 넘어가자.

Promiso는 그룹 기반 약속 관리 iOS 앱이다. 친구들과 그룹을 만들고, 약속을 잡고, 투표하고, 위치를 공유한다. Firebase 위에 전부 올라가 있다:

- **Firebase Auth** — Apple/Google 로그인
- **Firestore** — 메인 데이터베이스 (12개+ 컬렉션)
- **Cloud Functions** — 비즈니스 로직 50개+ 함수 (TypeScript)
- **Firebase Storage** — 프로필/그룹/약속 이미지
- **FCM** — 푸시 알림
- **Analytics, Crashlytics** — 모니터링

Cloud Functions 하나를 호출하는 게 아니라, **전체 백엔드가 Firebase다.** 이걸 통째로 자체 서버로 옮기겠다는 거다.

---

## 콜드스타트, 그리고 그 너머의 문제들

돌아가서, 콜드스타트 이야기.

Cloud Functions는 서버리스다. 요청이 오면 인스턴스를 띄우고, 일정 시간 요청이 없으면 내린다. 이 "다시 띄우는" 시간이 콜드스타트다. 유저가 느끼기엔 앱이 멈춘 것처럼 보인다.

Rust로 만든 서버는 다르다. Cloud Run 같은 컨테이너 서비스에 올리면, 바이너리가 밀리초 단위로 시작한다. 그리고 요청이 들어오면 마이크로초 단위로 응답한다. "기다리는 느낌" 자체가 사라진다.

하지만 콜드스타트만이 문제는 아니었다.

**비용**: Firestore는 읽기/쓰기당 과금된다. 실시간 리스너가 많은 앱에서는 유저가 늘수록 비용이 비례 이상으로 증가한다. PostgreSQL은 고정 비용이다. 예측 가능하고, 스케일 효율이 좋다.

**확장성**: Firestore는 문서당 초당 1회 쓰기 제한이 있다. JOIN이 안 된다. 그래서 데이터를 비정규화(같은 데이터를 여러 곳에 복사)해야 하는데, 이건 유지보수 지옥이다. SQL 데이터베이스에서는 JOIN 한 줄이면 끝나는 걸, Firestore에서는 트리거를 만들고 동기화 로직을 짜야 한다.

**락인**: Auth, Firestore, Functions, Storage — 전부 Firebase다. 가격 정책이 바뀌면? 서비스에 장애가 나면? 대안이 없다.

## 이 시리즈에서 다룰 것

이 시리즈는 **Swift iOS 개발자가 AI와 함께 Firebase 백엔드를 Rust 서버로 교체하는 전체 과정**을 기록한다.

기술 결정에서 삽질까지, 설계에서 배포까지. 모든 선택에는 비교군과 선택 근거가 따라온다.

다룰 내용을 간략히 정리하면:

- 아키텍처 설계와 기술 스택 선정
- Axum으로 API 서버 구축
- Firebase Auth를 자체 JWT 인증으로 교체
- Firestore를 PostgreSQL로 데이터 마이그레이션
- 50개+ Cloud Functions를 Rust API로 재작성
- 실시간 업데이트, LiveActivity, 푸시 알림
- Cloud Run 배포와 CI/CD
- iOS 앱의 네트워크 레이어 교체

다음 편에서는 전체 아키텍처를 설계한다. Firestore가 PostgreSQL이 되면 데이터 모델이 어떻게 바뀌는지, Cloud Functions가 Axum이 되면 API 구조가 어떻게 달라지는지.
