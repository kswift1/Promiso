# ADR-001: 백엔드 언어로 Rust 선택

## 상태

확정

## 맥락

Promiso iOS 앱은 Firebase (Auth, Firestore, Cloud Functions, Storage)를 전면 사용 중이다. Cloud Functions는 TypeScript로 작성된 50개 이상의 함수로 구성되어 있다.

Firebase를 자체 서버로 교체하려는 이유:
- **비용**: Firestore 읽기/쓰기 종량제. 실시간 리스너가 많아 유저 증가 시 비용 급증
- **성능**: Cloud Functions 콜드스타트 1~5초 (asia-northeast3 리전)
- **확장성**: Firestore 문서당 1write/sec 제한, JOIN 불가, 복합 쿼리 제약
- **락인**: Firebase 생태계에 전면 종속

백엔드 언어 후보: Rust, Go, TypeScript (현행 유지하며 플랫폼만 이전)

### 전제 조건

- AI(Claude)를 활용하여 코드를 작성하므로 **러닝커브와 DX는 평가 기준에서 제외**
- 채용 계획이 당장 없으므로 **채용 가능성도 제외**

## 평가 기준

| 기준 | 가중치 | 설명 |
|------|--------|------|
| 스케일 비용 | 높음 | 유니콘 지향. 유저당 서버 비용이 수익보다 낮아야 함 |
| 확장성 | 높음 | 10x~100x 성장 대응 |
| 안정성 | 높음 | 다운타임 = 유저 이탈 |
| 락인 | 중간 | 벤더 종속 회피 |
| 성능 | 높음 | 실시간 기능(LiveActivity, 투표)에서 체감 |
| 안전성 | 중간 | 프로덕션 버그 예방 |

## 비교

| 기준 | Rust | Go | TypeScript (현행) |
|------|------|-----|-------------------|
| 스케일 비용 | **최고** — GC 없음, 메모리/CPU 효율 극한. 같은 트래픽에 더 적은 인스턴스 | 좋음 — GC 있지만 경량. Rust 대비 2~3배 메모리 | 보통 — V8 오버헤드, 이벤트루프 단일 스레드 |
| 확장성 | 높음 — tokio 기반 async, 멀티스레드 | 높음 — goroutine 기반 동시성 | 높음 — Node 클러스터링, 그러나 CPU 바운드에 약함 |
| 안정성 | **최고** — 컴파일타임에 메모리/동시성 버그 차단. 런타임 패닉 극히 드뭄 | 좋음 — 단순한 언어 설계로 예측 가능. 다만 nil 참조 패닉 가능 | 보통 — 런타임 타입 에러, undefined 참조 |
| 락인 | 없음 — 네이티브 바이너리, 어디서든 실행 | 없음 — 동일 | Firebase SDK 종속 (현재). 플랫폼 이전만 하면 해소 |
| 성능 | **최고** — C/C++ 동급 성능, zero-cost abstraction | 좋음 — GC 일시정지 존재하나 마이크로초 수준 | 보통 — JIT 컴파일, GC, 이벤트루프 제약 |
| 안전성 | **최고** — ownership으로 데이터레이스 컴파일타임 차단, null 없음 | 좋음 — 단순하지만 nil, 데이터레이스 런타임 가능 | 약함 — any 타입, 런타임 에러 |

## 결정

**Rust를 선택한다.**

채용 가능성과 러닝커브를 제외하면 Rust가 모든 기준에서 우위이거나 동등하다. Go가 Rust를 이기는 항목이 없다.

특히 Promiso의 특성상:
- 실시간 기능(LiveActivity, 투표 실시간 반영)이 많아 **성능**이 중요
- 그룹 기반 서비스로 유저당 쿼리량이 많아 **스케일 비용** 최적화가 중요
- 소규모 팀에서 프로덕션 장애를 예방해야 하므로 **컴파일타임 안전성**이 중요

## 결과

- **얻는 것**: 최고 수준의 성능/비용 효율, 컴파일타임 안전성, 벤더 독립
- **잃는 것**: 채용 시 Rust 개발자 풀이 제한적 (현재는 해당 없음)
- **후속 결정**: 웹 프레임워크 선택 (→ ADR-002), DB 선택 (→ ADR-003), 배포 환경 선택 (→ ADR-004)
