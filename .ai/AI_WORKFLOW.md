# AI Workflow

모든 AI 도구(Claude Code, Codex 등)가 작업 시 따르는 공통 워크플로우.

---

## 작업 규모 분류

| 규모 | 기준 | 워크플로우 |
|------|------|----------|
| **XS** | 1 파일, 5줄 이내 (오타, import, 1줄 수정) | 메인 Claude 직접 수정→커밋[🔒] |
| **S** | 1~2 파일, 10줄 이내 | 탐색→구현→검증→커밋[🔒] |
| **M** | 3~5 파일, 1 모듈 | 전체 6단계 |
| **L** | 6+ 파일, 복수 모듈 | 전체 6단계 + 병렬 |

**XS 판단 기준**: 대상 파일과 수정 내용이 이미 명확하고, 탐색/계획/검증이 불필요한 경우.
애매하면 **S 이상으로 처리**.

---

## 6단계 워크플로우

```
0. 작업 공간 설정 [📋 유저 확인]
1. 탐색            🟢 자동
2. 계획            🔒 필수 승인 (M/L만)
3. 구현            🟢 자동
4. 검증            📋 유저 확인
5. 커밋            🔒 필수 승인
6. 후속            📋 선택
```

## 사용자 가시성 규칙

- 유저 승인/확인이 필요한 단계(0, 2, 4, 5)는 **commentary에만 남기면 안 된다**
- 승인 요청 내용은 **유저가 실제로 보는 final 응답에도 반드시 다시 포함**한다
- final에는 질문 한 줄만 보내지 말고, **핵심 범위/파일/검증/선택지 요약**을 함께 적는다
- 원칙: **final만 읽어도 유저가 다음 액션을 결정할 수 있어야 한다**

### 0. 작업 공간 설정
- 현재 브랜치 확인 (`git branch --show-current`)
- **Conductor 멀티 워크스페이스 환경**: 각 워크스페이스는 독립된 작업 디렉토리. 추가 worktree 생성 금지.
- Conductor가 아닌 환경에서 진행 중 작업과 충돌할 때만 Worktree 생성: `git worktree add ../Promiso-{브랜치명} -b {브랜치명} {base}`
- 브랜치 네이밍은 런타임/도구 지시를 우선하고, 별도 지시가 없으면 `fix/`, `feat/`, `refactor/`
- 유저 확인이 필요하면 commentary로 먼저 공유할 수 있지만, **final에도 같은 확인 포인트를 다시 적는다**

**Conductor 워크스페이스 간 협업**:
- 각 워크스페이스에는 `.context/` 디렉토리(gitignored)가 있음
- 다른 워크스페이스와 공유할 컨텍스트(결정사항, 의존성 정보 등)는 `.context/`에 파일로 저장
- 병렬 작업 시 동일 파일 수정 충돌을 피하기 위해, 작업 대상 파일 목록을 `.context/`에 기록

### 1. 탐색 — 🟢 자동
- 기존 코드 패턴과 의존성 방향 파악
- 영향 범위와 직접 관련된 `.ai/domain-rules/*.md`만 읽기 (필수)
- 영향받는 모듈/파일 식별 + 작업 규모 판단

**탐색 도구 선택 기준**:
- 대상 파일이 3개 이하이고 경로가 명확 → 메인 Claude가 Glob/Grep/Read 직접 사용
- 대상이 4개 이상이거나 탐색 범위가 불명확 → `Explore` 에이전트 위임

### 2. 계획 — 🔒 필수 승인 (M/L)
계획서 포맷:
```
## 구현 계획
### 작업 규모: S / M / L
### 작업 브랜치: {브랜치명}
### 생성할 파일
### 수정할 파일
### 작업 분배
| 순서 | 담당 | 작업 내용 | 직렬/병렬 |
### 의존성 영향 범위
### 검증 대상
```

- 계획 승인 요청은 commentary에만 두지 말고, **final에도 동일한 계획 요약 + 승인 질문**을 넣는다

### 3. 구현 — 🟢 자동
- 필요한 범위만 최소 수정, 요청되지 않은 광범위 리팩터링 금지
- 코드 변경 시: 모듈 단위 빌드 확인 (`make test-module MODULE={모듈명}` 또는 focused `tuist build`)
- 코드 변경 시: 빌드 실패 시 즉시 수정 후 재빌드
- 코드 변경 시: 테스트 추가/수정 필요 여부 판단 (`.ai/TEST_POLICY.md` + 관련 domain-rules 기준)
- 비즈니스 로직 변경, 버그 수정, 권한/제약 규칙 변경은 테스트를 기본값으로 고려하고, 생략 시 사유 보고
- 운영/관리 UI를 구현하거나 바꿀 때는 **실제 사용 순서, 대상 기준, 주의사항을 설명하는 가이드도 함께 포함**한다
- 원칙: 기능만 두고 끝내지 말고, **운영자가 화면만 보고 바로 사용할 수 있게 설명까지 같이 제공**한다

### 4. 검증 — 📋 유저 확인
1. `.ai/CONVENTIONS.md`와 관련 guide/schema 정합 규칙 기준으로 검토
2. 코드 변경 범위가 넓거나 커밋 전 최종 확인이 필요하면 `make test-changed` 실행
3. 코드 변경 시: 실행한 테스트와 미실행 테스트 범위 확인
4. 문서/설정 변경 시: 관련 guide/schema 정합성 확인 (빌드/테스트는 해당 시만)

보고 포맷:
```
## 구현 + 검증 결과
- 생성/수정 파일 목록
- 컨벤션: ✅/❌
- 빌드: ✅/❌/N/A
- 테스트: ✅/❌/N/A
커밋으로 진행할까요?
```

- 이 보고와 질문은 commentary에만 두지 말고, **final에 같은 형식으로 다시 제공**한다

### 5. 커밋 — 🔒 필수 승인
```
1. git status + git diff 확인
2. 커밋 메시지 초안 작성 (CONVENTIONS.md Git 규칙 준수)
3. 유저 승인 후 git add + git commit
```

- 커밋 승인 요청도 **final에 커밋 메시지 초안 또는 요약과 함께 다시 명시**한다

### 6. 후속 — 📋 선택
- PR 생성: 최신 `release/` 브랜치를 base로
- 다음 작업 제안

---

## 빌드 검증 규칙

| 규모 | 빌드 검증 |
|------|----------|
| **XS** | 불필요 (메인 Claude 판단에 위임) |
| **S** | 선택 (메인 Claude 판단에 위임) |
| **M/L** | 구현 완료 후 1회 필수 (`make test-module MODULE={모듈명}`) |

전체 빌드(`tuist build`)보다 모듈 단위 빌드를 우선 사용하여 시간 절감.

## 빌드 에러 복구 절차

빌드 실패 시 아래 절차를 따른다 (XS 규모로 직접 처리):

1. 에러 메시지 분석 → 원인 파일/줄 식별
2. 메인 Claude가 직접 수정 (에이전트 위임 불필요)
3. 재빌드 확인
4. 2회 실패 시 원인과 시도한 수정을 유저에게 보고

## 실패 복구

```
구현 ↔ 검증 최대 3회 반복
3회 초과 → 유저에게 에스컬레이션 (현재 상태 + 원인 + 시도한 해결 + 선택지)
```

---

## 공통 안전 규칙

- `.ai/DOMAIN_RULES.md` 및 `.ai/domain-rules/` 하위 파일은 사용자의 명시적 허락 없이 수정 불가
- 변경은 요청 범위에 한정하고, 모호하면 먼저 확인
- 관련 없는 변경은 사용자 확인 없이 버리지 않음
- 예상치 못한 변경을 발견하면 멈추고 진행 방향을 확인
- 명시적 요청이 없으면 amend commit 금지
