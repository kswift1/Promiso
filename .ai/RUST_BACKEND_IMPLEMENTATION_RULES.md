# Rust Backend Implementation Rules

> Rust 백엔드 구현 작업(`infra/rust-backend/`)에 적용하는 하드 게이트.
> 이 문서는 참고 자료가 아니라 실행 계약이다.
>
> 이 문서의 TDD 규칙은 `.ai/strict-coder/`의 3레이어 시스템으로 프로그래밍적으로 강제된다.
> - Layer 1 (Claude Code 훅): Red 없이 `src/` 수정 차단
> - Layer 2 (셸 스크립트): `tdd-red.sh` → `tdd-green.sh` 순서 강제
> - Layer 3 (git pre-commit): Red→Green 사이클 없이 커밋 차단

## 1. 적용 범위

- `infra/rust-backend/src/**`
- `infra/rust-backend/tests/**`
- `infra/rust-backend/migrations/**`
- `.ai/REST_API.md`
- `.ai/POSTGRES_SCHEMA.md`
- `docs/migration/{domain}.md`

Rust 백엔드 코드, 스키마, API 계약, Firebase → Rust 매핑 중 하나라도 바꾸면 이 문서를 따른다.

## 2. 우선순위

1. 런타임/시스템/사용자 직접 지시
2. 이 문서
3. 해당 도메인의 `.ai/domain-rules/*.md` 및 `.ai/TEST_POLICY.md`
4. `.ai/REST_API.md`, `.ai/POSTGRES_SCHEMA.md`, `docs/migration/{domain}.md`
5. 기존 Rust 백엔드 코드 패턴

충돌 시 더 상위 우선순위를 따른다.

## 3. 시작 게이트 — 선언 의무

코드를 한 줄이라도 수정하기 전에, 아래 항목을 유저에게 **명시적으로 선언**한다.

```
📋 시작 선언
- 활성 워크플로우: [이번 작업에서 따를 workflow 또는 guide]
- 우선순위 문서:
  1순위: ...
  2순위: ...
- 현재 단계: 분석 / Red / Green / Refactor / 문서 동기화 중 무엇인지
- 이번 단계 허용 행동: [이번 단계에서 할 수 있는 일]
- 이번 단계 금지 행동: [이번 단계에서 하면 안 되는 일]
- 대상 규칙: [이번 턴에 바꾸는 비즈니스 규칙 또는 API 계약]
- 검증 범위: [실행할 테스트 파일 또는 테스트 이름]
```

이 선언이 없으면 어떤 코드 수정도 시작하지 않는다.

아래 중 하나라도 불명확하면 구현으로 흡수하지 말고 `미결정 항목`으로 분리해 보고한다.

- Firebase 기존 동작이 무엇인지
- Rust에서 유지해야 할 외부 계약이 무엇인지
- DB 제약으로 내려야 하는 규칙인지, 서비스 레벨 규칙인지

## 4. 단계별 게이트 — TDD 강제

### 핵심 원칙

- **기본값은 한 턴에 한 단계다.**
- **같은 턴에서 다음 단계로 넘어가려면 사용자 지시 또는 예외 승인이 있어야 한다.**
- **각 단계는 진입 조건과 완료 증거가 있다.** 증거 없이 다음 단계로 넘어가지 않는다.
- **증거는 유저에게 보고한다.** 내부적으로 확인하고 넘어가지 않는다.
- **턴이 끝날 때는 final에도 같은 증거 요약을 다시 남긴다.**

### Phase 1: 분석

| 항목 | 내용 |
|------|------|
| **진입 조건** | 시작 게이트(섹션 3) 선언 완료 |
| **허용 행동** | 문서 읽기, 코드 읽기, 규칙 추출, 미결정 항목 분리 |
| **금지 행동** | 테스트 작성, 구현 코드 수정, 마이그레이션 작성 |
| **완료 증거** | 추출한 규칙 목록을 유저에게 보고 |

### Phase 2: Red — 테스트 작성

| 항목 | 내용 |
|------|------|
| **진입 조건** | Phase 1 완료 (규칙 목록 확인됨) |
| **허용 행동** | 테스트 파일 작성/수정, 테스트 컴파일에 필요한 최소 stub(빈 함수, 빈 구조체) |
| **금지 행동** | 서비스 로직 구현, 라우트 핸들러 구현, SQL 쿼리 작성 |
| **완료 증거** | `cargo test` 실행 결과에서 대상 테스트가 **실패(FAILED)**하는 출력을 유저에게 보고 |

```
❌ 금지: Red 증거 없이 "테스트를 작성했고, 당연히 실패할 것이므로" 구현으로 넘어가기
✅ 필수: cargo test 실행 → FAILED 출력 확인 → 실패 테스트 목록과 이유를 유저에게 보고
```

**프로그래밍 강제**: `.ai/strict-coder/scripts/tdd-red.sh --test {test_file}` 실행.
실패 확인 후 `.tdd-state`에 기록되어야 Phase 3 진입이 가능하다 (Layer 1이 차단).

### Phase 3: Green — 구현

| 항목 | 내용 |
|------|------|
| **진입 조건** | Phase 2의 Red 증거가 유저에게 보고됨 |
| **허용 행동** | 서비스, 라우트, 모델, 마이그레이션 구현 |
| **금지 행동** | 새로운 테스트 케이스 추가, 기존 테스트 삭제/약화, 테스트 기대값 변경 |
| **완료 증거** | 같은 `cargo test` 명령으로 대상 테스트가 **전부 통과(ok)**하는 출력을 유저에게 보고 |

**프로그래밍 강제**: `.ai/strict-coder/scripts/tdd-green.sh` 실행.
통과 확인 후 `.tdd-state`가 green으로 갱신되어야 커밋이 가능하다 (Layer 3이 차단).

### Phase 4: Refactor (선택)

| 항목 | 내용 |
|------|------|
| **진입 조건** | Phase 3의 Green 증거가 유저에게 보고됨 |
| **허용 행동** | 구조 정리, 중복 제거, 네이밍 개선 (동작 변경 없이) |
| **금지 행동** | 새 기능 추가, 테스트 동작 변경, 요청 범위 외 리팩터링 |
| **완료 증거** | 회귀 테스트 전체 통과 출력 |

### Phase 5: 문서 동기화

| 항목 | 내용 |
|------|------|
| **진입 조건** | Phase 3 또는 Phase 4 완료 |
| **허용 행동** | `.ai/REST_API.md`, `.ai/POSTGRES_SCHEMA.md`, `docs/migration/{domain}.md` 갱신 |
| **금지 행동** | 구현 코드 수정 |
| **완료 증거** | 동기화한 문서 목록을 유저에게 보고 |

### 전체 금지 사항

- `Red` 증거 없이 구현 시작
- 사용자 승인 없이 테스트와 구현을 같은 턴에 섞어서 한 번에 제출
- "당연히 실패할 것이다"로 Red를 대체
- 구현 편의를 위해 테스트를 삭제하거나 기대값을 약화
- 미정인 규칙을 추측으로 확정해 넣기
- 요청 범위를 넘어 도메인 전체를 리팩터링

## 5. 예외 프로토콜

단계 순서를 바꾸거나 건너뛰어야 한다고 판단하면, **코드를 수정하기 전에** 아래를 유저에게 보고하고 승인을 받는다.

```
⚠️ 예외 요청
- 현재 단계: [어디에 있는지]
- 변경 내용: [무엇을 바꾸려는지]
- 이유: [왜 필요한지]
- 리스크: [이렇게 하면 뭐가 위험한지]
- 대안: [다른 방법이 있다면]
```

- 승인 없이 예외를 적용하면 안 된다.
- "효율적이니까", "어차피 같은 결과니까"는 예외 사유가 아니다.
- 승인받은 예외는 해당 턴에만 유효하다. 다음 턴에서는 원래 순서로 복귀한다.

## 6. 테스트 규칙

### 6.1 기본 원칙

- 비즈니스 규칙은 테스트 이름으로 드러나야 한다.
- 테스트는 구현 상세가 아니라 규칙, 권한, 경계값, 외부 계약을 증명해야 한다.
- `Green`만으로 충분하지 않다. 먼저 `Red` 증거가 있어야 한다.

### 6.2 테스트 위치

- DB 없는 순수 규칙: 서비스 단위 테스트
- DB 제약, 권한, 쿼리, 트랜잭션: `#[sqlx::test(migrations = "./migrations")]`
- HTTP 계약, 인증 경계, 응답 shape: 라우터 통합 테스트 또는 기존 API 테스트 패턴 재사용

### 6.3 최소 커버리지

변경이 있으면 아래 중 해당되는 항목을 기본값으로 포함한다.

- 경계값: min/max, empty, trimmed, invalid format
- 권한: 허용 케이스 + 거부 케이스
- 중복/충돌: unique, already joined, duplicate create
- 동시성 위험: read-check-write 경쟁 조건이 있는 흐름
- 외부 계약: 상태 코드, 에러 코드, JSON 필드 shape

## 7. 구현 규칙

### 7.1 레이어 경계

- 라우트는 입력 파싱, 인증 컨텍스트 수신, 서비스 호출, `ApiResponse` 반환만 담당한다.
- 비즈니스 규칙과 SQL은 서비스 레이어에 둔다.
- 요청/응답 DTO는 `models/`에 둔다.
- 성공 응답은 `ApiResponse`, 실패 응답은 `AppError`로만 수렴한다.

### 7.2 PostgreSQL 우선 재설계

- Firebase의 비정규화 구조를 그대로 옮기지 않는다.
- 복사본 동기화, 숨은 trigger 의존, fan-out write를 기본 해법으로 선택하지 않는다.
- PostgreSQL에서 표현 가능한 규칙은 JOIN, FK, UNIQUE, CHECK, transaction으로 먼저 해결한다.

### 7.3 트랜잭션과 제약

아래 조건 중 하나라도 만족하면 트랜잭션을 기본값으로 사용한다.

- 2개 이상 테이블을 함께 갱신
- 읽고 검사한 뒤 쓰는 흐름
- 중간 실패 시 부분 성공이 남으면 안 되는 흐름
- 정원, 중복, host 이전처럼 경쟁 조건 가능성이 있는 흐름

표현 가능한 불변식은 두 군데에서 잠근다.

- 서비스 레벨 검증: 사용자 친화적 에러 반환
- DB 제약: CHECK, UNIQUE, FK, partial index 등으로 최종 보장

둘 중 하나만으로 끝내지 않는다.

### 7.4 쿼리 규칙

- 목록/상세 조회는 N+1보다 JOIN 또는 서브쿼리를 우선한다.
- 같은 요청 경로에서 동일 데이터를 반복 조회하지 않는다.
- 성능상 예외가 필요하면 이유를 코드 코멘트나 결과 보고에 남긴다.

### 7.5 에러 규칙

- 요청 처리 경로에서 panic 기반 제어 흐름을 추가하지 않는다.
- 외부에 노출되는 에러 코드는 기존 Firebase/iOS 계약과 호환되게 유지한다.
- 내부 상세는 `AppError::Internal`로 감추고, 사용자 메시지와 내부 원인을 분리한다.

### 7.6 DTO 규칙

- 공개 요청 DTO는 허용 필드가 닫혀 있어야 하는지 먼저 판단한다.
- 불필요한 필드 유입을 막아야 하는 요청은 `#[serde(deny_unknown_fields)]`를 기본값으로 고려한다.
- partial update는 현재 코드베이스의 `Option<Option<T>>` 패턴처럼 삭제/유지/변경이 구분되게 표현한다.

## 8. 문서 동기화 규칙

### 8.1 스키마 변경

- SSOT는 `infra/rust-backend/migrations/*.sql`
- 스키마가 바뀌면 `.ai/POSTGRES_SCHEMA.md`를 함께 갱신한다.

### 8.2 API 변경

- 요청/응답 필드, 상태 코드, 인증 요구사항이 바뀌면 `.ai/REST_API.md`를 함께 갱신한다.

### 8.3 매핑 변경

- Firebase 함수가 어느 Rust 엔드포인트로 이전됐는지 바뀌면 `docs/migration/{domain}.md`를 함께 갱신한다.

### 8.4 ADR 필요 조건

아래는 같은 작업에서 ADR 검토 대상이다.

- 공통 아키텍처 패턴 변경
- 인증/에러/스케줄링 같은 횡단 관심사 변경
- 여러 도메인에 반복 적용될 새 구현 원칙 도입

## 9. 작업 보고 형식

각 Phase 완료 시 아래 형식으로 유저에게 보고한다. 내부적으로 확인하고 넘어가지 않는다.

### Phase 2 (Red) 완료 보고

```
🔴 Red 완료
- 실행 명령: cargo test --manifest-path infra/rust-backend/Cargo.toml --test {test_file} -- --exact {test_name}
- 실패 테스트 수: N개
- 실패 목록:
  - test_name_1: 실패 이유
  - test_name_2: 실패 이유
- 규칙 대조: Step 2 규칙 N개 중 N개 테스트 매핑 완료
```

### Phase 3 (Green) 완료 보고

```
🟢 Green 완료
- 실행 명령: cargo test --manifest-path infra/rust-backend/Cargo.toml --test {test_file} -- --exact {test_name}
- 통과 테스트 수: N개
- 전체 결과: ok (N passed, 0 failed)
- 변경 파일: [목록]
```

### Phase 5 (문서 동기화) 완료 보고

```
📄 문서 동기화 완료
- 동기화한 문서: [목록]
- 미결정 항목: [있으면 나열, 없으면 "없음"]
```

## 10. 빠른 체크리스트

### 매 턴 시작 시
- [ ] 시작 게이트 선언했다 (섹션 3)
- [ ] 현재 단계의 진입 조건을 만족했다

### Red Phase
- [ ] 테스트만 작성했다 (구현 로직 없음)
- [ ] `cargo test` 실행해서 FAILED 출력을 확인했다
- [ ] 실패 결과를 유저에게 보고했다

### Green Phase
- [ ] Red 증거가 유저에게 보고된 상태다
- [ ] 기존 테스트를 삭제하거나 약화하지 않았다
- [ ] `cargo test` 실행해서 ok 출력을 확인했다
- [ ] 트랜잭션/DB 제약 필요 여부를 점검했다
- [ ] 통과 결과를 유저에게 보고했다

### 마무리
- [ ] API/스키마/매핑 문서를 동기화했다
- [ ] 미결정 항목을 분리해 보고했다
